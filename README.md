# 地图画搭建机器人（双机器人 · 网页控制台）

使用 [Mineflayer](https://github.com/PrismarineJS/mineflayer) 在 Minecraft 服务器里自动搭建地图画（地毯画）的机器人程序。

- **双机器人并行**：两个账号共享一串施工任务，谁有空谁领下一个，速度约为单机器人的两倍；
- **按颜色整批施工**：统计整张画的材料后，一种颜色拿一次材料、一次做完，几乎不用切换快捷栏和背包；
- **极速放置模式**：不逐块等待服务器确认，按颜色分组后同一 tick 连发多个放置包；16 种地毯也只换十几次手持，不受 9 格快捷栏限制（默认开启）；
- **网页控制台**：上传投影、填写账号、开始/停止、查看进度与实时俯视建造图；
- **实时俯视图**：暗色为待建预览，彩色为已建方块，随施工实时刷新；
- **失败兜底**：某个机器人掉线时，它没做完的区块会自动交给另一个机器人；重启后已建好的方块会自动跳过。

本文只涉及地图画相关程序（`painting.js`、`server.js`、`public/index.html`）。

---

## 1. 环境要求

| 项目 | 要求 |
| --- | --- |
| Node.js | 建议 18 及以上（仓库开发环境为 Node 26） |
| Java | 可选。`.litematic` 现在由程序直接解析；只有直接解析失败时才会退回 Lite2Edit 转换，那时才需要 Java |
| Minecraft 账号 | 两个**不同**的账号，支持 `microsoft`（正版）或 `offline`（离线） |
| 服务器权限 | 机器人需要有创造模式/飞行、打开材料容器、在搭建区域放置方块的权限 |

## 2. 安装

首次使用先安装依赖：

```bash
npm install
```

---

## 3. 启动

启动网页控制台：

```bash
npm run web
```

等价于 `node server.js`。启动成功后终端会输出：

```text
地图画搭建网页 UI 已启动
  本地访问: http://localhost:8080
```

浏览器打开 <http://localhost:8080> 即可。

改端口（默认 8080）：

```powershell
# PowerShell
$env:PORT = 8090
npm run web
```

```bash
# CMD / bash
set PORT=8090 && npm run web
```

> 说明：`npm start` 是旧的单机器人命令行入口，现在只会在终端提示改用网页控制台，不会真正启动建造。

## 4. 使用步骤

在网页控制台上按顺序操作：

1. **填写服务器连接信息**
   - 服务器地址 / 端口 / 版本（默认 `wolfx.jp:25565`，版本 `1.20.4`）；
   - 两个机器人账号必须不同，否则服务端会直接拒绝；
   - 两个账号会**间隔 5 秒依次连接**（页面上的"账号连接间隔"可调），避免服务器提示"连接速度过快"被踢；
   - 认证方式选 `microsoft` 时，两个账号会依次弹出登录验证，首次登录请耐心完成。
2. **上传投影文件**
   - 支持 `.schem` 和 `.litematic`；`.litematic` 直接解析（不经过 Lite2Edit，避免部分转换把数据解错位），上传时就能发现格式问题；
   - 如果遇到程序解析不了的 `.litematic`，会自动退回 Lite2Edit 转换（需要 Java）；
   - 上传大小上限 200MB。
3. **设置搭建坐标**
   - 起始 X / Y / Z 表示投影文件原点 `(0,0,0)` 对应的实际世界坐标；
   - 当前地图画的参考值：X `37439`、Z `13887`（Y 按实际平台填写）。
4. **开始建造**
   - **放置模式**：默认"极速"（同一 tick 连发，适合无反作弊的服务器）；如果服务器有反作弊或出现被踢，换成"稳定"即可逐块确认；
   - "每个机器人连续放置数"默认 4：同一个站位能放到的相邻方块会一次发出去；卡顿或被服务器警告时调回 1~2；
   - 点击"开始建造"后，先连接两个机器人，再开始搭建；随时可点"停止"。

## 5. 界面说明

- **状态徽章**：空闲 / 正在连接 / 搭建中 / 完成 / 出错；
- **机器人状态条**：显示两个账号的实时状态，例如"搭建区块 [1,2]""连接失败""已完成分配任务"；
- **进度条与统计**：两个机器人合并统计的方块进度、已用时间、预计剩余时间、当前区域与当前方块；
- **实时建造图（俯视）**：
  - 暗色像素 = 计划要放的方块（整张画的预览）；
  - 彩色像素 = 已经建好的方块，随建造实时刷新；
  - 鼠标悬停在某一格可查看它的 X/Z 坐标、方块名和建造状态；
- **运行日志**：连接、取料、传送、异常等信息都记在这里。

## 6. 建造原理（简述）

1. 解析投影，得到"每格放什么方块"的清单，并**统计每种颜色的总数量**（这个总量决定每种颜色要分几趟取料）；
2. 两个账号间隔若干秒依次进服；**两个账号进服后都保持正常落地状态**，不会悬空；搭建中如果重生，会自动恢复飞行（`multiplayer.disconnect.flying` 防护）；
3. **先建光边**：把光边方块（默认 `smooth_stone`）单独分组，两个机器人合力先整条造完，这一步只取光边的材料；
   - 光边时机器人站在**光边方块正上方一格**（X/Z 保持不变）从上往下放，不走 z-1；
   - 光边放得**更慢更稳**（每次瞬移/放置后额外等 `edgePlaceDelayMs`，默认 100ms），避免差一截；
4. **再按颜色施工**：光边完成后，把同一种颜色的所有方块放在一起做——取这一种颜色的材料 → 把这一种颜色的格子全部放完 → 再换下一种颜色。**一种颜色只换一次手持**，不再频繁切换快捷栏和背包；
   - 一种颜色的数量超过背包容量时（默认每批 `colorBatchSize = 1600` 格，约 25 组）自动切成多批，取一批、放一批、再回去取；
   - 颜色内部按行蛇形排序，走位最短；
   - 从背包拿材料时会**先把整组搬进空的快捷栏格**（尽量填满 9 格），每次搬完等 `takeItemDelayMs`（默认 50ms）；以后换这一种颜色**只切快捷栏栏位（不等待、不动背包）**，总拿取次数最少；
5. **取材料的找箱顺序**：先开基准箱子（y），没货就往同一 x/z 的 **y+1、y+2、y+3、y+4** 找；一层层拿，够用为止；
   - 如果 y ~ y+4 全都没有库存，机器人会**原地等待补货**（材料箱从下往上慢慢补），每隔 `restockWaitMs`（默认 15 秒）检查一次，补足后自动继续搭建；
   - 取材料前会确认机器人**确实站在材料箱旁边**：如果因为传送失败、被挪走或区块没加载而够不到箱子，会自动重新 `/res tp hpdth` 再取，不会误判成"没库存"而干等（网页状态会显示"未到达 xxx 材料箱，重新传送取货"）；
   - 取完材料回搭建平台也一样：如果 `/res tp hpdth.dth` 没生效（机器人和**网页输入的起始搭建坐标**差超过 `platformTpMaxDistance`，默认 32 格），会自动重发传送指令重试，最多 `platformTpRetries`（默认 3）次；
   - 去箱子旁边**不用寻路，直接瞬移**（优先找箱子旁边的空位站，找不到就站箱子正上方），所以不会像寻路那样把 hpdth 里挡路的方块挖掉；
6. **每一格放置前都会检查机器人是不是站在方块旁边**（眼睛到参考方块的距离 ≤ `placeReach`）：不在旁边就移动过去再放——距离太远服务器会直接拒绝放置；
   - **地图画（非光边）**：站到目标方块 **z-1** 那一格（本层已经建好的那排地毯；还没铺就站下一层的地毯）上落地站稳；
   - **光边**：站到方块正上方一格（X/Z 不变）悬空放置；
   - 移动用的是**分段瞬移**：服务器限制 X/Z 一次最多 32 格、Y 一次最多 9 格，超了会被拒绝；程序会先分段把 Y 调到"比方块高一格"的安全高度，再分段移动 X/Z，段与段之间留 `teleportStepDelayMs`（默认 10ms），最后落到站位高度；
   - 取材料去箱子旁边也是同一套分段瞬移；
7. 两个机器人共享同一串任务队列（光边任务在最前，然后是各种颜色的批次）：谁做完谁领下一个，同一种颜色的不同批次可以并行，不会出现一个机器人闲着等另一个；
8. 每个任务放完后会检查实际结果，没放上的方块用稳定模式逐块补建；漏放率偏高时自动放慢爆发间隔，几乎不漏时自动加快；某个机器人掉线时它的任务会回到队列由另一个接手，建造结束前还会做一轮收尾补建。

## 7. 可调参数

所有参数都在 `painting.js` 文件顶部的 `SETTINGS` 里：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `host` / `port` / `version` / `auth` | `wolfx.jp` / `25565` / `1.20.4` / `microsoft` | 连接默认值，网页上填写的值会覆盖 |
| `spawnTimeoutMs` | 5 分钟 | **仅**限连接+登录+准备工作；建造过程不受它影响 |
| `connectIntervalMs` | 5000 | 两个账号的连接间隔（毫秒）；服务器提示"连接速度过快"时调大（页面同名字段可改） |
| `standOnGround` | true | 放置时站在目标方块 z-1 那格的地毯上（不悬空）；设为 false 恢复原来的悬空方式 |
| `standWaitMs` | 120 | 站好位置后等位置同步的时间（毫秒），服务器卡时可调大 |
| `placeReach` | 4 | 放置距离上限（眼睛到参考方块中心）；不在这个范围内会先移动到方块旁边 |
| `edgePlaceDelayMs` | 100 | 建造光边时每次瞬移/放置后的额外等待（毫秒），调大更稳 |
| `fastPlace` | true | 极速模式总开关；false = 稳定模式（逐块等待服务器确认） |
| `burstSize` | 32 | 极速模式下每批连发多少个放置包，然后让出一次事件循环 |
| `burstIntervalMs` | 50 | 极速模式下两批之间的间隔（毫秒），也是自适应调节的起始值 |
| `burstMoveWaitMs` | 60 | 极速模式开始时瞬移到区块中心后，等待位置同步的时间（毫秒） |
| `refillWaitMs` | 150 | 一叠材料用完后，等服务器同步背包再补一叠的等待（毫秒） |
| `verifyTimeoutMs` | 3000 | 每个区块放完后，最多等多久确认方块是否真的放上（毫秒） |
| `adaptiveBurst` | true | 按每个区块的漏放率自动增减爆发间隔 |
| `edgeBlock` | `smooth_stone` | 先单独建造的"光边"方块；设为 `null` 则不分阶段、和地图画一起建 |
| `placeConcurrency` | 4 | 每个机器人一次连续放置的方块数（同一材料且在放置距离内），网页下拉框可调 1~4 |
| `placeIntervalMs` | 30 | **稳定模式**下每个机器人两批放置之间的间隔（毫秒） |
| `takeItemDelayMs` | 50 | 从背包拿物品（搬进快捷栏/换到手上）后的等待（毫秒）；只切换快捷栏不会等待 |
| `retryDelayMs` / `placeRetries` | 120 / 3 | 放置失败后的重试间隔与次数 |
| `teleportWaitMs` | 5000 | 每次 `/res tp` 传送后的等待（毫秒） |
| `jumpWaitMs` | 400 | 跨区块瞬移时的等待（毫秒） |
| `teleportStepXZ` | 32 | 分段瞬移时 X/Z 每段最多多少格（服务器限制） |
| `teleportStepY` | 9 | 分段瞬移时 Y 每段最多多少格（服务器限制） |
| `teleportStepDelayMs` | 10 | 分段瞬移的延迟：走满一段（XZ 32 / Y 9 格）才 sleep，没满就直接完成不等 |
| `retryDelayMs` | 120 | 放置失败后的重试间隔（毫秒） |
| `jobRetryDelayMs` | 500 | 任务处理失败后重新领取的延迟（毫秒） |
| `goalNearTimeoutMs` | 10000 | 靠近容器时寻路的超时（毫秒） |
| `foodItem` / `foodReserve` / `foodThreshold` | `cooked_cod` / 64 / 15 | 食物种类、携带数量、低于多少饥饿值自动进食 |
| `storageTp` / `platformTp` | `/res tp hpdth` / `/res tp hpdth.dth` | 材料仓与搭建平台的传送指令，按你的服务器地标修改 |
| `platformTpMaxDistance` | 32 | 回平台后与起始搭建坐标差多少格算传送失败 |
| `platformTpRetries` | 3 | 回平台失败时最多重试传送几次 |
| `chestStackDepth` | 4 | 箱子没货时往上找 y+1 ... y+4（只变 Y，x/z 不变） |
| `chestReach` | 32 | 与材料箱的距离在这个范围内就算"已到材料区"，直接分段瞬移过去开箱 |
| `restockWaitMs` | 15000 | y~y+4 都没货时，原地等补货的检查间隔（毫秒） |
| `colorBatchSize` | 1600 | 每种颜色每批最多处理多少格（超过就分批取料，背包 36 格上限约 2304） |
| `regionSize` | 32 | 取料与建造的区块尺寸 |
| `chunkRetries` | 3 | 单个区块最多重试几次，超过后跳过（日志里会记录） |
| `verbose` | false | 改为 true 会打印每个方块的详细日志 |

### 材料仓坐标

`painting.js` 里的 `materialChests` 数组定义了"颜色 → 容器坐标"的对应关系，需要按你服务器上的实际摆放修改：

```js
{ color: 'white_carpet', pos: new Vec3(37541, 90, 13880), type: 'barrel' },
{ color: 'food', pos: new Vec3(37518, 90, 13881), type: 'chest', food: true },  // 食物箱
```

要求：

- 每种颜色一个容器（木桶或箱子均可），容器内的方块名要与 `color` 一致（如 `white_carpet`）；
- 地毯类支持三层堆叠：`y`、`y+1`、`y+2` 位置上的容器会依次尝试；
- 食物箱里放 `cooked_cod`，机器人食物不足时会自动补充（默认带到 64 个）。

## 8. 常见问题

**Q：建造要 10~20 分钟，会不会触发 `spawnTimeoutMs` 超时？**

不会。该超时只覆盖"连接服务器 + 登录 + 进入游戏 + 准备工作"这段过程，机器人一进入游戏计时器就失效了；搭建过程再久也不受影响。

**Q：两个微软账号登录很久会超时吗？**

首次登录如果超过 5 分钟没完成验证，对应机器人会被判为"连接超时"。可以把 `spawnTimeoutMs` 调大（例如 `10 * 60 * 1000`）；登录过一次后一般会走缓存，速度会快很多。

**Q：机器人被踢，提示"连接速度过快 / Connection too fast"？**

这是服务器的连接限速。程序现在默认让两个账号**间隔 5 秒依次连接**；如果服务器限制更严，把网页上"账号连接间隔"改成 10 秒或更大再试（也可以在 `painting.js` 里改 `connectIntervalMs`）。

**Q：机器人被踢，提示 `multiplayer.disconnect.flying`？**

服务器没有开允许飞行（`allow-flight=false`），悬空超过约 4 秒就会被判定为飞行踢出。程序现在**不悬空**：放置时会先站到目标方块 **z-1 那一格**（当前这层已经建好的地毯，或下一层的地毯）上，站稳后再放。只有在目标附近完全没有地面（边界等特殊情况）时才会短暂悬空一格。

**Q：网页一直显示"等待补货"？**

先看状态文字：

- "**未到达 xxx 材料箱，重新传送取货**"：机器人没走到箱子旁边（传送失败/被挪走），程序会自动 `/res tp hpdth` 重试，不需要手动干预；
- "**等待补货 xxx（还差 N）**"：机器人已经站在箱子旁，但 y ~ y+4 五层箱子确实都没有这种材料了，它在原地等材料补给（材料箱从下往上补），补足后自动继续。

**Q：机器人会把 hpdth 里的方块挖掉？**

之前是寻路插件（pathfinder）干的：它默认允许挖方块/垫方块来开路。现在取材料的移动已经改成**直接瞬移**，代码里不再使用寻路，不会再破坏 hpdth 的方块。

**Q：机器人卡在 `hpdth.dth` 传送点不过来铺？**

是服务器的瞬移距离限制导致的：服务器的瞬移一次最多 X/Z 32 格、Y 9 格，超过就会被拒绝，机器人看起来就"卡在原地"。现在程序会**分段瞬移**（先分段调 Y 到比方块高一格的安全高度，再分段移动 X/Z，每段间隔 10ms），不会再出现这种卡住。

**Q：机器人取了材料后站着不动好几秒？**

以前每放完一批会等服务器确认最多 3 秒；现在改成"连续 600ms 没有新方块被确认就不再等"，只会短暂停顿。

**Q：机器人被服务器踢了怎么办？**

把网页上"每个机器人同时放置数"调回 1，或把 `placeIntervalMs` 从 30 调大到 60~100 再试。服务器对移动/发包限制较严时，宁可慢一点。

**Q：极速模式会不会把服务器打爆？放漏了怎么办？**

极速模式默认每个机器人每批连发 32 个放置包、批间隔 50ms，并且自带两层保护：

1. 每个区块放完后会核对实际结果，没放上的方块自动用稳定模式补建（不会漏）；
2. 如果某个区块漏放率超过 15% 会自动放慢爆发间隔，低于 2% 又会自动加速，逐步逼近服务器能承受的最快速度，日志里会打印调整过程。

放置顺序按颜色分组（同色一起放），所以就算 16 种地毯全都用上，一个区块也只需要换十几次手持——不依赖 9 格快捷栏，换手次数与颜色数成正比，而不是与方块数成正比。

想更快可以把 `burstSize` 调大到 64 或把 `burstIntervalMs` 调小；服务器出现卡顿、回弹或大量补建时把它调回去即可。有反作弊的服务器请改用"稳定"模式。

**Q：上传 `.litematic` 报错？**

`.litematic` 默认由程序直接解析，正常情况不需要 Java。上传时报"直接解析失败"并退回 Lite2Edit 时，才需要本机安装 Java（`java -version` 能执行）。如果两种方式都失败，说明投影文件本身可能不完整，用 Litematica 重新导出后再试。

**Q：为什么不用 Lite2Edit 转换了？**

实测发现部分 `.litematic` 经 Lite2Edit 转换后数据会错位（画出来是斜条纹），所以现在优先直接读取 `.litematic` 原始数据，转换只作为兜底方案。

**Q：8080 端口被占用？**

用 `PORT` 环境变量换端口启动（见"启动"一节）。

**Q：中途停止了，能接着建吗？**

可以。重新开始建造时会自动跳过已经存在的方块，俯视建造图也会把已建好的部分显示出来。

**Q：提示"两个机器人都未能连接"？**

检查服务器地址/端口/版本、账号密码或登录状态、服务器是否开启了正版验证（开了就用 `microsoft`，没开可用 `offline`）。

## 9. 如何生成 `.schem` 投影文件

1. **WorldEdit 插件**
   - 游戏内用 `//pos1`、`//pos2` 选择区域；
   - `//copy` 复制选区；
   - `//schem save <文件名>` 保存为 `.schem`。
2. **MCEdit 工具**
   - 打开 MCEdit 并加载世界 → 选择要导出的区域 → "导出选区" → 选择 `.schem` 格式。
3. **Litematica**
   - 用 Litematica 导出 `.litematic`，再用 [Lite2Edit](https://github.com/GoldenDelicios/Lite2Edit/) 转成 `.schem`；
   - 也可以直接在网页上上传 `.litematic`，由服务器自动调用 Lite2Edit 转换。
